# HO: Hand-offs and remote calls

Base catalog 1.1.0. Scope: messaging between owners, acknowledgement, idempotency, retries, deadlines, dead letters, sagas, reconciliation. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| HO-01 | Every hand-off between owners MUST travel on one durable, persisted messaging channel with declared retention. Never as a hand-off: a direct call or a webhook consumed directly, an in-memory queue, a table two owners write, a file drop, email, or a job comparing two systems. A synchronous interaction is allowed only as HS-03 (interactive command to the owner), HS-04 (read) or HS-12 (data-plane transfer) state it; a deviation is recorded under HO-37. | Enterprise Integration Patterns: Messaging, Message Channel, Guaranteed Delivery | By which channel does each fact, command or obligation leave its owner? |
| HO-02 | A hand-off is published only after the source committed: by change-data capture or the owner's change stream, by an outbox, or by a step that publishes the outcome of an effect it just committed and acknowledges its own input only after that publish is confirmed. No process writes two owners, or an owner and the channel, in one step. | Transactional Outbox pattern; Enterprise Integration Patterns: Transactional Client | Is there a dual write, or a publish before commit? |
| HO-03 | Every message carries: an id deterministic from the source (never random at retry), a versioned type, the aggregate key, the owner's commit time, correlation and causation ids, and trace context. | CloudEvents 1.0 (id, type, subject, time; distributed-tracing extension); Enterprise Integration Patterns: Correlation Identifier, Format Indicator | How is each message id derived, and is it stable across a retry? |
| HO-04 | A message carries identifiers and small facts within a stated size bound. Bytes (files, exports, models) stay in their store and travel as reference, size and checksum. | Enterprise Integration Patterns: Claim Check | Does any payload carry bulk bytes or exceed the stated bound? |
| HO-05 | Each producer and consumer has its own broker identity limited to its channels, over an encrypted link. A tenant id in an address is routing, never authorization. | NIST SP 800-53 Rev. 5 AC-6, SC-8 | Does each party have its own scoped identity, and is anything authorized by address text? |
| HO-06 | Input is acknowledged only after the receiving owner durably received the obligation: the broker confirmed the publish, the owner's transaction committed, or the orchestrator persisted the execution. Before that, a retryable failure leaves the input unacknowledged; after it, the receiver owns execution, retry, outcome and repair. An in-progress signal never leases downstream completion. | Enterprise Integration Patterns: Guaranteed Delivery, Transactional Client | At which exact boundary is each input acknowledged? |
| HO-07 | Each edge has exactly one retry owner with bounded attempts. Nested retries are prohibited (a proxy and a client both retrying; an orchestrator retrying a task whose client retries). No retry, back-off or restart setting is added to outlast a race or ordering gap; the order is fixed on the dependency's readiness. The retry bound outlasts the dependency's stated longest tolerated outage, so a transient outage is not dead-lettered. | Google SRE book ch. 22 (Addressing Cascading Failures: retries) | Who retries each edge, is a second retry layered on it, and does any retry exist to get past an ordering gap? |
| HO-08 | After the retry bound, or on a non-retryable failure, a reference (never the payload) with the original channel, position, reason and correlation id goes to a dead-letter channel and an alert fires. Release is an explicit, audited operator action. Silent drops and unbounded retries are prohibited. | Enterprise Integration Patterns: Dead Letter Channel, Invalid Message Channel | Where does an undeliverable item go, who is alerted, and how is it released? |
| HO-09 | Order is per aggregate key. Where order matters, consumption is serialized per aggregate partition and names the write it protects. Global serialization is prohibited; consumers tolerate out-of-order delivery across aggregates and reject a stale version by the owner's revision. | Enterprise Integration Patterns: Message Sequence; Convention: per-key ordering with stale-version rejection | Where order matters, what scopes it, and is anything serialized globally? |
| HO-10 | Work that changes more than one owner is an orchestrated process with persisted state: one step per owner, a timeout per step, a compensation for each recorded effect, and a terminal state of succeeded, compensated or failed (needs an operator). Choreography by events is allowed only for independent notification or projection consumers. | Enterprise Integration Patterns: Process Manager; Saga (Garcia-Molina and Salem, 1987) | Does any multi-owner change run outside an orchestrated process with compensations and a terminal state? |
| HO-11 | Each integration declares a reconciliation of owner keys and totals against the target: read-only, bounded, started by an owner event, never by a schedule of ours. A difference alerts and triggers a replay or corrective flow. A read that fails, returns null or is truncated fails the run and never reports zero differences; a failed child counts as a difference. It never replaces the hand-off. | Google SRE book ch. 26 (Data Integrity: out-of-band checks) | What starts each reconciliation, and what does it report when its read fails or is cut? |
| HO-12 | Calls to an external provider pass through one throttle per provider account, set below the provider's published limit; a rate-limit answer's retry delay is honoured within the deadline. | Google SRE book ch. 21 (Handling Overload: client-side throttling); RFC 6585 section 4 (429 with Retry-After) | What limits the call rate to each provider, and how is a rate-limit or quota answer handled? |
| HO-13 | A message notifies of a committed fact or requests an effect; it is never the fact. A consumer that needs current state rereads the exact committed revision from the owner. | Convention: the owner is the truth, a message is a notification | Does any consumer act on message content where it needs current owner state? |
| HO-14 | Each event type has a schema in the repository, checked against recorded sample events. A change inside a version is additive only and consumers ignore unknown fields. A breaking change is a new type version; the producer publishes both until every declared consumer moved, then retires the old one. | Enterprise Integration Patterns: Format Indicator; Convention: additive-only change within a version | Does a change alter an existing type incompatibly, or retire a version a consumer still reads? |
| HO-15 | A message never carries tokens, secrets, signed URLs or personal data beyond the minimum keys. Authority for an asynchronous effect is the recorded decision id plus the target owner's own authorization of the consumer's workload identity. | Convention: minimal message payload content | What is in each payload, and whose identity authorizes the effect? |
| HO-16 | Delivery is at least once, so every effect MUST be idempotent on the event id or a business key derived from it, by (in order of preference) a target-native key (upsert, PUT, declarative apply, unique natural key), else a provider idempotency key sent with the call, else a persistent idempotency repository. Memory-only deduplication and a broker's duplicate window are not idempotency. | Enterprise Integration Patterns: Idempotent Receiver | What makes a second delivery of each effect a no-op? |
| HO-17 | When a remote call times out or its connection drops after sending (an apply carried over a remote shell included), the outcome is unknown: the caller MUST query the target with the idempotency key before any retry, or rely on a target-native or provider idempotency key. A non-idempotent mutation is never retried blind. | Convention: query before retry after timeout | After a timeout or lost connection on each mutating call, what is read before it is repeated? |
| HO-18 | Each integration declares its handling per failure class: retryable (timeout, 429, 503, connection error) is retried; non-retryable (400, 404, validation, schema mismatch) is quarantined at once; authorization (401, 403) is quarantined at once and a security alert fires; conflict (409) is resolved by reread from the owner, then acknowledged or quarantined. | Enterprise Integration Patterns: Dead Letter Channel, Invalid Message Channel; Convention: handling per failure class | For each remote call, what happens on 400/404, 401/403, 409, 429 and 5xx? |
| HO-19 | Every remote call and every multi-step process has an absolute deadline. The remaining budget travels with the call; no layer resets or extends it; each timeout is shorter than the caller's remaining budget. On an asynchronous edge the deadline is checked at each delivery, so a deadline quarantine is at most one redelivery interval late. | Release It! 2nd ed. Timeouts | Does every call have a timeout derived from the caller's remaining budget, and can anything extend it? |
| HO-20 | Each target dependency has one circuit breaker and a bulkhead (a bounded pool or concurrency). While the breaker is open, consumers stop pulling instead of spending retries. Queue depth and consumer lag have alert thresholds. | Release It! 2nd ed. Circuit Breaker, Bulkheads | For each dependency, what stops calls when it fails, and what bounds concurrent use? |
| HO-21 | Business time is the owner's commit time, never the consumer's clock. Periodic work is keyed by its period (`2026-10`), so a rerun is idempotent. Nothing waits by a sleep loop or poll. | Convention: owner commit time, period keys | Which clock stamps each fact, and what keys a periodic run? |
| HO-22 | Each integration emits: published, delivered, redelivered, acknowledged, quarantined, consumer lag, effect latency (commit to effect) and reconciliation differences. `traceparent` links the owner commit, the message and the effect. Each integration has a lag objective and a quarantine-rate objective. | W3C Trace Context (traceparent); Google SRE book ch. 6 | Which of these signals exists for each edge, and where is it read? |
| HO-23 | Each hand-off names the one hand-off scenario (HS) row that governs it and uses only that row's mechanism. | Convention: one governing scenario per hand-off | Which HS row governs each hand-off, and does the design match it? |
| HO-24 | Each hand-off names its pattern from the Enterprise Integration Patterns catalogue and uses the owner's mechanism or one shared implementation for it. No pattern is reimplemented and no template cloned; a pattern is implemented once, with its observability, and reused. | Enterprise Integration Patterns | Which catalogue pattern does each step use, and is any pattern rebuilt by hand? |
| HO-25 | Before an edge is built, its declaration holds exactly: source and target, the native call or configuration reference, stream and consumer settings, acknowledgement boundary, idempotency key, retry owner, deadline, DLQ and principal. It restates nothing the owner defines (schemas, flags, return codes, guarantee prose, test lists). | Convention: complete edge declaration before build | Is each edge's declaration complete before build, and free of copied owner text? |
| HO-26 | In flow, route and transformation code: parse once, read once, guards first, set once, pure transforms, one straight effect path. Calls fail explicitly; nothing catches and continues or defaults a missing owner fact; the caller gets only the reads and writes its effect needs. | Convention: explicit failure, no catch-and-continue | Is any error swallowed, or any absent value replaced by a default? |
| HO-27 | A business refusal ends its execution as failed and publishes a typed refusal outcome with reason and business keys; a log line or counter is no outcome. A message is skipped (and counted) only when it is not addressed to the consumer, never when a precondition of the requested effect is missing. | Convention: typed business refusal outcome | How does each refusal surface, and when is a message skipped? |
| HO-28 | The owner's client handles documented status and retry; the caller adds only the one retry owner, the deadline, ambiguous-outcome resolution and quarantine. A refusal counts as success only as the owner's duplicate signal on a caller-chosen key, confirmed by reread; any other failure reports status, error type and bounded detail, never the raw body. | Convention: single retry owner, bounded error detail | What does each call treat as "already done", and what does a failure print? |
| HO-29 | Code hosted inside an owner (its hooks, server-side scripts, database triggers) never performs a hand-off or a remote call to another owner. | Convention: no cross-owner calls from in-owner code | Does any code inside an owner's process call another owner? |
| HO-30 | A fact required after the pivot (the commit after which the process can no longer be compensated) is checked by its owner once, at that commit, on every route into it (UI, API, import, workflow action), before any irreversible effect. Later steps reread, never recheck. An owner that cannot refuse on every route is unavailable. | Convention: check once at the pivot commit | Where is each post-pivot fact checked, and can any route bypass it? |
| HO-31 | An operation id is bound to its exact payload and schema version. A known id arriving with a different payload is refused (409 or 422), never applied and never acknowledged as a duplicate. | IETF draft-ietf-httpapi-idempotency-key-header (a key is never reused with a different payload) | What does each receiver do with a known id carrying a different payload? |
| HO-32 | A quarantine counts only when the write of its dead-letter reference is confirmed by the broker. If that write fails, the consumer keeps responsibility (no acknowledgement) or propagates the failure; a log line is never a quarantine. | Enterprise Integration Patterns: Dead Letter Channel, Guaranteed Delivery; Convention: a quarantine counts only when confirmed | What happens when the dead-letter write itself fails? |
| HO-33 | A release from quarantine, a re-drive or a replay keeps the original `id` and runs under the consumer's authorization at execution time. A decision or principal revoked since first delivery stops the effect; nothing captured at first delivery authorizes it. | Convention: replay under current authorization | Can a replay act for a principal whose grant was revoked since the first delivery? |
| HO-34 | A transformation (translator, enricher, splitter, normalizer) acknowledges its input only after the confirmed publish of its versioned output. A command has exactly one effect handler. A required observer is its own durable consumer; a wire tap serves only rebuildable observers. | Enterprise Integration Patterns: Message Translator, Content Enricher, Splitter, Normalizer, Wire Tap, Guaranteed Delivery | Can a transformation acknowledge before its output is durable, or a required observer hang off a wire tap? |
| HO-35 | Deduplication, aggregation and process state that a durable obligation depends on is in a persistent repository, with its retention, capacity and recovery objectives declared. | Enterprise Integration Patterns: Idempotent Receiver, Aggregator; Convention: persistent state for durable obligations | Is any aggregator, dedup set or saga state in memory only? |
| HO-36 | Each guarantee an edge adds names its conformance test: duplicate (same id twice gives one effect), target down (effect lands after restore, no loss), crash after effect before acknowledgement (no second effect), poison (quarantined on first attempt, others unaffected), ordering (final state equals the newer version), ambiguous outcome (query before retry, one effect), reconciliation (a deleted row is detected and repaired), replay (state unchanged). An integration counts as qualified only after those tests pass. | Convention: conformance test per added guarantee | Does the design claim an integration qualified without the tests of the guarantees it adds? |
| HO-37 | A deviation from a hand-off rule is a recorded exception naming the rule, the reason, the bound on loss or duplication, the compensating control or reconciliation, and the trigger to remove it. An undocumented deviation is a break. | Convention: architecture decision records (Nygard, "Documenting Architecture Decisions") | Is every deviation a recorded exception with its bound and removal trigger? |
| HO-38 | A versioned input carries a generation and a content digest. A consumer applies a generation only if it is newer than the applied one, and an unchanged digest is a no-op even when the generation advanced. | Enterprise Integration Patterns: Idempotent Receiver; Convention: generation and digest check | Does an old generation or an unchanged digest re-apply? |
| HO-39 | In an orchestration or integration flow, every split, slice, condition, comparison and calculation is written in the engine's own expression or query language inside the flow, one named program per step; no script task or external interpreter carries logic. Each program has fixtures for its normal, difference and absent-input cases. | Enterprise Integration Patterns: Message Translator; Convention: one engine per flow | Is any logic in a script task, and does each program have fixtures? |
| HO-40 | A wake-up signal that is not durable (a database notification such as PostgreSQL LISTEN/NOTIFY, an in-process event, an unpersisted push) is only a hint that the durable channel or table holds new work; it is never the hand-off and never the only record of the work. Its consumer drains the durable backlog from its last acknowledged position on start, on restart, after every reconnection and on each hint, so a signal lost while the consumer was down, disconnected or busy loses no work. The hint replaces polling (RL-08); a periodic re-scan is never added to cover a lost hint. | Enterprise Integration Patterns: Guaranteed Delivery, Event-Driven Consumer; Kubernetes API Concepts, "Efficient detection of changes" (list, then watch from the listed resourceVersion; re-list after 410 Gone); PostgreSQL 18 documentation, LISTEN and NOTIFY (a notification reaches only sessions listening when it is delivered) | For each wake-up signal: is it durable, and if not, what does the consumer read on start, restart and reconnection to pick up work signalled while it was away? Name a signal whose loss loses or delays work until a later signal. |
