# CI: Concurrency and isolation

Base catalog 1.0.0. Scope: serializers, locks, single writer, bulkheads between installations and tenants. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| CI-01 | Each shared resource has exactly one serializer and none overlaps another (one release run per installation, one converge per host, the IaC tool's lock for state). | Single-writer principle; Release It! 2nd ed. Bulkheads | What serializes each shared resource, and do two serializers cover one? |
| CI-02 | A second concurrent release of the same installation is refused, never queued or merged. | Single-writer principle; Release It! 2nd ed. Bulkheads | What happens when a release starts while one runs for the same installation? |
| CI-03 | Mutual exclusion uses native locks, leases and fencing only; no marker file, PID file or flag of ours. | Single-writer principle; Release It! 2nd ed. Bulkheads | Is any mutual exclusion implemented by our own file or flag? |
| CI-04 | No probe and no second apply overlaps a converge of the same target. | Single-writer principle; Release It! 2nd ed. Bulkheads | Can a status check or another run touch a target mid-converge? |
| CI-05 | A shared record or file has one writer; readers check its version before acting. A file derived from several installations is regenerated from their separate inputs, never edited by each. | Single-writer principle; Release It! 2nd ed. Bulkheads | Who writes each shared input, and can two installations write one file? |
| CI-06 | One object comes from one source: no two writers of one object or field, and no shared mutable state between parallel steps. | Single-writer principle; Release It! 2nd ed. Bulkheads | Which objects or fields do two parallel steps or two tools both write? |
| CI-07 | On a shared host, each installation's units, inputs and telemetry are partitioned so that one installation's failure, missing input or slow step neither fails nor blocks another installation's converge or release; the shared host's telemetry does not depend on any one installation. | Release It! 2nd ed. Bulkheads | If installation A's inputs are broken or its step hangs, what happens to B's run? |
| CI-08 | A run or remediation acts only on its own labelled installation; it never writes, prunes or remediates another installation's objects. | Single-writer principle; Release It! 2nd ed. Bulkheads | Does any step of one installation's release write, prune or repair something that belongs to another? |
| CI-09 | Per-installation parts of a shared owner's configuration live in the owner's include or drop-in mechanism, are checked by the owner before load, and are applied by the owner's reload, never by a restart or by editing the shared file. | PostgreSQL "The pg_hba.conf File", `pg_hba_file_rules`, `pg_reload_conf()`; systemd.unit(5) | How does one installation change shared configuration without editing the shared file or dropping others' sessions? |
| CI-10 | A failing package blocks only its descendants. | Single-writer principle; Release It! 2nd ed. Bulkheads | What else stops when one package fails? |
| CI-11 | A test gives back every shared bounded resource in teardown, pass or fail; consumption that cannot be returned is not shared. | Single-writer principle; Release It! 2nd ed. Bulkheads | What shared resource does each test consume, and when is it returned? |
| CI-12 | One shared, independently scaled store per kind, with each tool or tenant isolated by its own database, role and credentials; never a copy of the store per tool or tenant. A separate instance needs a documented reason (blast radius, incompatibility, compliance boundary). | Multi-tenant isolation practice; Release It! 2nd ed. Bulkheads | How is each user of a shared store separated, and is a second store added? |
| CI-13 | A held lock is a fault to report: a run never waits a lock out or breaks it automatically. A stale lock is released only by the owner's own unlock, as a named runbook step, after a person confirmed its holder is gone. | Lease and fencing practice (Kleppmann, Designing Data-Intensive Applications ch. 8) | What does a run do when it finds the lock held, and how is a stale lock cleared? |
