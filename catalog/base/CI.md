# CI: Concurrency and isolation

Base catalog 1.1.0. Scope: serializers, locks, single writer, bulkheads between installations and tenants. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| CI-01 | Each shared resource has exactly one serializer and none overlaps another (one release run per installation, one converge per host, the IaC tool's lock for state). | Single-writer principle; Release It! 2nd ed. Bulkheads | What serializes each shared resource, and do two serializers cover one? |
| CI-02 | A second concurrent release of the same installation is refused, never queued or merged. | Single-writer principle; Release It! 2nd ed. Bulkheads | What happens when a release starts while one runs for the same installation? |
| CI-03 | Mutual exclusion uses native locks, leases and fencing only; no marker file, PID file or flag of ours. | Convention: native locks only | Is any mutual exclusion implemented by our own file or flag? |
| CI-04 | No probe and no second apply overlaps a converge of the same target. | Convention: no probe overlaps a converge | Can a status check or another run touch a target mid-converge? |
| CI-05 | A shared record or file has one writer; readers check its version before acting. A file derived from several installations is regenerated from their separate inputs, never edited by each. | Single-writer principle; Release It! 2nd ed. Bulkheads | Which shared record or file has two writers, or a reader that acts without a version check? Name the file and the writers. NA where the design has no shared record or file. |
| CI-06 | One object comes from one source: no two writers of one object or field, and no shared mutable state between parallel steps. | Single-writer principle; Release It! 2nd ed. Bulkheads | Which objects or fields do two parallel steps or two tools both write? |
| CI-07 | On a shared host, each installation's units, inputs and telemetry are partitioned so that one installation's failure, missing input or slow step neither fails nor blocks another installation's converge or release; the shared host's telemetry does not depend on any one installation. | Release It! 2nd ed. Bulkheads | Which input, unit or telemetry path of installation A, when broken or hung, fails or blocks installation B's run? Name it. NA where no host is shared between installations. |
| CI-08 | A run or remediation acts only on its own labelled installation; it never writes, prunes or remediates another installation's objects. | Single-writer principle; Release It! 2nd ed. Bulkheads | Which step of one installation's run writes, prunes or repairs which object of another installation? Name the step and the object. |
| CI-09 | Per-installation parts of a shared owner's configuration live in the owner's include or drop-in mechanism, are checked by the owner before load, and are applied by the owner's reload, never by a restart or by editing the shared file. | Convention: per-installation include files, validated and reloaded by the owner | How does one installation change shared configuration without editing the shared file or dropping others' sessions? |
| CI-10 | A failing deployable unit (package) blocks only the units that declare a dependency on it; siblings and other installations proceed. | Single-writer principle; Release It! 2nd ed. Bulkheads | What else stops when one deployable unit fails? |
| CI-11 | A test gives back every shared bounded resource in teardown, pass or fail; consumption that cannot be returned is not shared. | Convention: tests return shared resources | What shared resource does each test consume, and when is it returned? |
| CI-12 | One shared, independently scaled store per kind, with each tool or tenant isolated by its own database, role and credentials; never a copy of the store per tool or tenant. A separate instance needs a documented reason (blast radius, incompatibility, compliance boundary). | Convention: shared-store multi-tenancy | How is each user of a shared store separated, and is a second store added? |
| CI-13 | A lock without a lease (a state lock, a migration lock) that is found held is a fault to report: a run never waits a lock out or breaks it automatically. A stale lock is released only by the owner's own unlock, as a named runbook step, after a person confirmed its holder is gone. | Convention: a lock with an unconfirmed holder is escalated, not broken | What does a run do when it finds the lock held, and how is a stale lock cleared? |
| CI-14 | In a system that places data by tenant, cell or shard, every table row, event and message carries its placement key (the tenant, cell or shard id that decides where it is stored and which partition it goes to) as a field of its own. The key is set at creation from the trusted entry decision, never derived later by a join or lookup, and never changed in place (a move is a copy to the new placement and a deletion at the old). A write without the key is refused, and every uniqueness that must hold within one placement includes the key. NA where the system has a single placement (one tenant, one cell, no sharding). | Azure Architecture Center, Sharding pattern ("Issues and considerations": the shard key); Citus documentation, "Choosing Distribution Column" (multi-tenant: the tenant id in every table; unique constraints include the distribution column) | Which table, event or message lacks its placement key as its own field, takes it by a join or lookup, or allows it to change in place? Name it. |
