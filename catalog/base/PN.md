# PN: Plans

Base catalog 1.0.0. Scope: step format a junior can follow, gates, traceability, real-flow evidence, rollback order. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| PN-01 | Each step states: File (path with a symbol, state id or grep anchor, never a line number), Do (the exact edit or command), Expect (the owner's read-back), Verify, and If it fails. | Runbook practice | Does every step carry all five parts? |
| PN-02 | No step leaves a decision to the implementer: no "decide", "choose", "as appropriate" or "e.g." in an instruction. A junior engineer can follow it to a successful result without thinking or deciding. | Runbook practice | Which steps need judgement? |
| PN-03 | An unproven claim is a gate step with both outcomes written in advance. | Convention: unproven claim is a gate | Which claims has nothing run yet, and what does the plan say for each result? |
| PN-04 | The plan never contradicts its spec; the spec is rewritten in place in the same pass. | Convention: plan never contradicts spec | Where do plan and spec differ? |
| PN-05 | Per-setup values in commands come from the installation record and are checked against the machine (host name, current user, repository root); no literal host, user or path. | Twelve-Factor App III (config separate from code) | Which command would fail or act on the wrong machine in another setup? |
| PN-06 | The plan records a dry run of its first steps by a reader with no context, and lists each guess that reader had to make; every guess is a plan defect to fix. | Runbook practice | Is the dry run recorded, and are its guesses fixed? |
| PN-07 | The plan names its user-visible outcome, non-goals, dependencies and delete list (unnecessary features, duplicate mechanisms, replaced wiring), and cites the governing specifications and decisions without reopening them. | Convention: plan states outcome and non-goals | Are outcome, non-goals and delete list present? |
| PN-08 | Every normative requirement maps to its journey, acceptance id, evidence owner and task. | Convention: requirement-to-task traceability | Which requirement of the spec has no task? |
| PN-09 | The end-to-end flow is mapped before structure is chosen: input, native owner and binding, validation, effect, hand-off, completion and recovery; consumers, trust boundaries, what each owner must not own, lifecycle transitions, timeout, cancel and error paths. | Convention: map the flow first | Is the flow from input to completion and recovery written, with each owner's limits? |
| PN-10 | The plan reuses before it extends, searches the fix history of the engines and areas it touches, cites the fixes and engine-behaviour notes it relies on, and does not re-decide what a past fix settled. | Convention: reuse and cite past fixes | Which earlier fixes in the touched areas does the plan cite? |
| PN-11 | Code a plan gives verbatim has passed the project's commit check in a scratch tree before the plan is approved; the plan's own text is not evidence that it parses or runs. | Convention: verbatim code is pre-run | Was each verbatim block run through the check? |
| PN-12 | The plan names its reliability profile, classifies stored sources (authority, projection or ephemeral) before design, and gives budgets for affected hot stages. | Convention: plan states reliability profile | Are the profile, the classification and the budgets stated? |
| PN-13 | Tasks are small and vertical, each with one owner, files, inputs and outputs, prohibited writes, dependencies and a real-flow gate, with scoped cutover, rollback, cleanup and removal of replaced wiring. | Convention: small vertical tasks | Does each task name its prohibited writes and its gate? |
| PN-14 | Acceptance is through real staged services, deterministic native seeds and public entry points. No mock, fake store or test-only path is feature proof. Source checks, native-runtime evidence and public-journey evidence are reported separately. | Convention: acceptance through real services | What proves each task, and is any proof a mock or a source check? |
| PN-15 | A step's verification is the real call and the owner's response or read-back; a step that changes an install path includes its empty-machine run. | Convention: verify by owner read-back | Which step is verified only by its own exit code or text? |
| PN-16 | A step that cannot pass stops the work and reports the gap; it is never worked around and never passed by weakening a check or test (PR-08). | Convention: failing step stops work | What does each step say to do when it fails, and does any branch weaken a check? |
| PN-17 | Irreversible steps come after every step that can refuse, and each cutover has its rollback. | Convention: irreversible steps last | Which step cannot be undone, and what precedes it? |
| PN-18 | The plan records a bounded second-pass audit with concrete corrections or open gaps (architecture alignment, requirement coverage, native reuse, root cause, proportionate durability, dead paths, resource lifetime, copies, test realism). | Convention: second-pass plan audit | Is the audit present with findings, not ticks? |
| PN-19 | A target with no surface (zero-copy where no data path exists) is marked not applicable, never padded. | Convention: not applicable, never padded | Is any target claimed that the work cannot affect? |
