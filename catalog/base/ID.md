# ID: Identity and secrets

Base catalog 1.1.0. Scope: secret custody and transport, least privilege, rotation, revocation, tenant isolation of access. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| ID-01 | No secret appears in process arguments, logs or messages. A token is passed on standard input or by a file (a registry credential by an auth file, a webhook token on standard input). | NIST SP 800-53 Rev. 5 IA-5(7) | Where does each secret travel, and is it ever an argument or printed? |
| ID-02 | A signing key is held in a managed key service or HSM, or signing is keyless with a short-lived certificate; no private key lands on a host and no key file exists. Verifiers hold only the public key or trust root. | NIST SP 800-53 Rev. 5 SC-12 | Where does each private key live, and what can read it? |
| ID-03 | Every account, binding and principal is a declared resource of an IaC root with a named duty and a removal path when the duty ends; none is created or changed by hand. | NIST SP 800-53 Rev. 5 AC-2, CM-3 | For each new principal: who owns it, what declares it, what removes it? |
| ID-04 | Consumers pick up a re-issued credential at once, by event, never only after a periodic refresh. | Convention: event-driven credential pickup | After a rotation, what makes each consumer pick up the new value? |
| ID-05 | Revocation removes the credential at its consumer first, then its account or state. An account whose duty ended is disabled or removed; a person's own account is not a duty account, and the end of one membership ends that membership's access, never the person's account (LC-42). | NIST SP 800-53 Rev. 5 AC-2(3) | Which credential does the design remove at its account or state before its consumer, or which ended duty keeps a live account? Name it. NA where the design removes no credential and ends no duty. |
| ID-06 | A read error is never treated as absence: a generated-once value is never regenerated or overwritten because its read failed. Creation is the owner's check-and-set (written create-if-missing behind a guard read). | Convention: generated-once check-and-set | What happens when the read of an existing secret fails? |
| ID-07 | Every adapter derives its scope from trusted identity, holds least privilege and short-lived credentials, fails closed when authorization cannot be decided, has a tenant-denial test, and exposes no raw backing store or provider secret. Web surfaces meet OWASP ASVS 4.0.3 level 2 (or the level the project states, never below 2 for a surface handling tenant data). | NIST SP 800-53 Rev. 5 AC-6; OWASP ASVS 4.0.3 | Which adapter or web surface, on which request, acts without a decided authorization, holds a wider or long-lived credential, or exposes a raw store or provider secret? Name it. NA where the design adds or changes no adapter or web surface. |
| ID-08 | Cross-tenant resolution returns the same unknown-or-unauthorized result in every case; it reveals no node count, owner, timing difference or object existence. | Convention: uniform unknown-or-unauthorized result | Can a caller in tenant A learn that an object of tenant B exists? |
| ID-09 | The ingress is the sole entry for backend, authentication, RPC and admin traffic. Public URLs come from the declared profile and trusted forwarding metadata; cross-origin access admits exact origins only. A development security exception is explicit and unavailable in production. NA where the artifact has no inbound surface (it accepts no traffic). | NIST SP 800-53 Rev. 5 SC-7 | Does any service take traffic or identity other than through the ingress? |
| ID-10 | A secret reaches a workload only from the secret store, by a declared reference the platform resolves. None is written by hand or carried in a deployable artifact. When the store is unavailable, readers do not start; there is no second custody. | NIST SP 800-53 Rev. 5 SC-12, SC-28 | Which secret reaches which workload by a path other than a declared reference to the secret store, or which reader starts while the store is down? Name the secret and the path. |
| ID-11 | Each duty (plan, apply, release, read) has its own identity holding the least its steps need. Each automated step runs with a short-lived credential of its own duty; people hold no standing deployment roles. | NIST SP 800-53 Rev. 5 AC-5, AC-6 | Under which identity does each step run, and which grant does it hold that it never uses? |
| ID-12 | A credential is short-lived and scoped to its operation: a step's deadline never exceeds the credential's lifetime minus a grace period. | NIST SP 800-53 Rev. 5 IA-5, AC-6 | How long does each credential live against the step that uses it? |
| ID-13 | A rotation is one versioned, declared change; a first apply never changes a secret a running system uses. Verifiers accept the current and previous key until everything retained is re-signed. A static key has a stated maximum age. | NIST SP 800-53 Rev. 5 IA-5, SC-12 | How is each credential rotated, and what keeps working during it? |
| ID-14 | A design never relies on a permission nobody granted. A wider grant is an explicit project-owner decision, quoting the grant that exists and the grant needed; widening and narrowing a grant are separate changes. | NIST SP 800-53 Rev. 5 AC-2, AC-6 | Which step needs which permission that no declared grant gives? Name the step and the permission. |
| ID-15 | Authentication, token verification, request or message signature verification and the request's authorization decision run once per trust boundary, in the one enforcement mechanism at the point where material enters it (an ingress, a service's entry, a consumer's receipt of a message). Blocks behind that point receive the verified principal, claims and decision as values and act on them. They never re-parse or re-verify the token or signature, never re-fetch keys for it, and never repeat the decision. A block handed no verified result refuses (ID-07). An ingress that verifies and forwards to its services over a link only it can use (mutual TLS, or a network path each service admits from the ingress alone) is the trust boundary for those services; they take its verified result and do not verify again. Any other entry into a service, and each asynchronous consumer acting as its own workload identity (HS-17), is its own boundary with its own single check. A check that needs data only the owner holds is made by that owner once: at its commit (HO-30) or, for a read, in its own query scoped by the principal it was handed. A long-lived session, stream or connection re-runs the entry check at the entry, never behind it, when its credential expires (ID-12), is rotated (ID-04) or is revoked, or when its policy names a re-evaluation event. Release-artifact signatures are governed by SC-05 and SC-14, not by this rule. NA where the artifact accepts no authenticated or signed material. | OWASP ASVS 4.0.3 V1.4.1, V1.4.4 (one trusted enforcement mechanism that every request passes through); NIST SP 800-207 §2, Fig. 1 (traffic past the PEP shares one level of trust; the implicit trust zone is kept as small as possible) and §2.1 tenet 6 (re-evaluation during a session by policy); Convention: one verification per trust boundary, none behind it; an ingress on an exclusive link may be the boundary for several services | For each service and consumer, where are the token, signature and authorization decision verified on entry, and is any link into the service usable by anything but that entry? Which block behind that point verifies again, re-fetches a key, repeats the decision or acts without the verified result handed to it? What re-runs the entry check of a long-lived session on expiry or revocation? Name the block. |
