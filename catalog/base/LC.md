# LC: Lifecycle and ownership

Base catalog 1.0.0. Scope: levels, parent-first acquisition, child-first release, crash recovery, one owner per fact, lineage. Each row is the whole rule; judge it from the row alone.

The default lifecycle model. A project may tighten it in its overlay. A project that uses another level model states the mapping of its levels to L0-L6 in its overlay header; the rows are then read through that mapping.

| Level | What lives there | Acquired when | Released by |
|---|---|---|---|
| L0 deployment | the installation's record and profile | validated, no conflicting instance | never while a descendant is acquiring, ready or draining |
| L1 substrate | host, network, data roots, cluster, storage and backup domains | L0 ready; device, path, network and capacity qualified | draining every descendant; durable roots kept unless destruction is approved |
| L2 durable authorities | databases, object and file stores, secret store, message streams, backup repositories | all L1 handles ready; native format and identity observed | stopping writers, flushing, revoking leases; bytes retained |
| L3 immutable configuration | schemas, migrations, policies, routes, workflows, charts | affected L2 ready; signed input digest; native validate succeeds | replacing by version; never deleted while referenced |
| L4 services and controllers | ingress, applications, operators, workers, gateways | hard L1-L3 parents ready; capability preflight succeeds | closing admission, draining, stopping |
| L5 operations | jobs, executions, deliveries, sessions, backups and restores | L4 ready; deadline, tenant and inputs bound | ending terminal; claims returned, credentials revoked |
| L6 durable results | business records, files, datasets, artifacts, evidence | an explicit L5 operation or user action; owner commit verified | only by the owner's deletion policy |

Capsule: the versioned state record of one persistent service (owner and class, format, digest, path, migration and backup authority, compatibility, parent generation).

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| LC-01 | Every managed resource MUST name its level (L0-L6) and be ordered and readied by its platform's reconciler or its owner's native dependency and readiness mechanism. Our code and configuration never re-encode an order or readiness model. | Dependency-ordered resource lifecycle practice (RAII; controller reconciliation) | Does each handle name its level and the native authority that orders and readies it, with no order or readiness model of ours? |
| LC-02 | Acquisition MUST be parent-first and release child-first. No parent stops, resets or is deleted while a descendant holds an active borrow, claim or write. | Dependency-ordered resource lifecycle practice (RAII; controller reconciliation) | For each create, stop and delete path: is the order parent-first in, child-first out, and what checks that no descendant still borrows? |
| LC-03 | A change of version or input MUST dirty the changed node and its exact transitive hard descendants automatically. Only dirty nodes are evaluated; only the owner's native terminal evidence cleans a node; no person has to remember to re-run a dependent. | Convention: transitive dirty-node evaluation | What marks a node dirty, what cleans it, and does a person ever have to remember a re-run? |
| LC-04 | Each effect MUST declare its hard parents (each resource it needs, its level, the native readiness observed) and what it does before a parent is ready: unreachable (parent-first order, or a field the owner requires at the parent's creation), wait (the owner's native wait) or deferred (re-driven by the parent's commit event). Where no event exists the case is a named boundary, never a schedule. A hard parent is never at a higher level than its dependent: a lower level never waits on a higher-level product, shared infrastructure never waits on a tenant's output, and a bootstrap step uses only what exists before it, never a product of the thing it bootstraps. | Convention: declared parent-readiness behaviour | Does each effect list its hard parents, their readiness signal and its before-parent behaviour, with no timer as fallback, and does any lower-level or bootstrap step wait on something created above or after it? |
| LC-05 | An L0 deployment record is used only when validated (signed or schema-checked) and no conflicting instance exists. It never stops, resets or archives while any descendant is acquiring, ready or draining. | Convention: validated deployment record guard | Is the instance record validated before use, and is its stop or reset guarded by its descendants' state? |
| LC-06 | An L1 substrate handle (host, network, data roots, cluster, storage and backup domains) needs its exact L0 ready and its device, path, network ownership and capacity qualified. Its release closes new L2 acquisition, drains every descendant and retains durable roots unless that exact destruction is approved. | Convention: level-ordered substrate handle | Is capacity (disk, inodes) checked before use, and which approval permits destroying an L1 durable root? |
| LC-07 | An L2 durable authority needs all its L1 handles ready and its native format and identity observed. Its release stops writers and ingress, checkpoints or flushes, revokes leases and retains the authoritative bytes; only declared projections and caches are rebuilt. | Convention: durable authority release order | Does any path release or recreate an L2 authority without stopping writers and retaining its bytes? |
| LC-08 | L3 configuration needs every affected L2 authority ready, an exact signed input digest, and the owner's native validate or migrate to succeed. It is replaced by a new version and never live-deleted while an L4-L6 descendant references it. | Convention: immutable configuration replacement | Can the design delete or overwrite configuration a running descendant still reads, or apply configuration the owner did not validate? |
| LC-09 | An L4 service needs all hard L1-L3 parents ready and its exact capability preflight to succeed. Its release closes admission first, drains or hands back work, then stops. Loss of a stateless process never deletes L2 or L6 state. | Convention: close admission before stop | Is admission closed before stop, and can a restart or kill of the process lose durable state? |
| LC-10 | An L5 operation needs its L4 services ready and binds, at entry, a trusted entry decision, an absolute deadline, its tenant or installation and immutable input references. It ends terminal, checkpointed or cancelled with its owner, returns its claims and revokes its credentials; its parent cannot stop until it is terminal or safely fenced. | Convention: bounded operation with terminal state | Does each run, job or execution carry a deadline and end in a terminal state that returns what it held? |
| LC-11 | An L6 durable result is written only by an explicit L5 operation or a native user action, with the owner's durable commit and immutable references verified. A normal stop retains it; it is deleted only when its owner permits, retention expired, no legal hold or retained descendant needs it, and a tombstone is left (DS-04). | Convention: durable result written by owner | Is every durable result committed by its owner, and is any deletion of one gated by the owner's policy? |
| LC-12 | An L4 peer that a service routes to is an observed target, never a hard parent (the ingress starts with an application down and shows a truthful state; its hard parents are network, certificate and route configuration). The dependency graph has no cycle. | Convention: routed peer is observed target | Is any observed route target declared as a hard parent, and does the graph contain a cycle? |
| LC-13 | A shared database engine is one L2 handle; every logical database on it has its own semantic owner, role, schema, migration, backup inventory and readiness status. An application process is L4; its database, writable files, object store, queue, index and secret are separate L2 resources, whatever the vendor's packaging merges. A compound owner gets one capsule per subsystem and one coordinated consistency gate across them; no owner holds another's bytes or metadata. | Convention: one handle per store | Is each store of a compound owner a separate handle with its own readiness and backup? |
| LC-14 | A projection, search index or cache is a separate L2 projection unless declared authoritative. Its source version and its deterministic rebuild action are hard parents; after loss it is rebuilt from the recorded immutable source generation and its fingerprint verified. Its loss is never silently reported as success or as product-data loss. | Convention: rebuildable projection from recorded source | Does each derived store name its source and rebuild path, and what does its loss report? |
| LC-15 | A backup repository MUST sit in a failure domain independent of its source. The source never depends on the backup client or repository to serve normal writes. | NIST SP 800-53 Rev. 5 CP-6, CP-9 | Where does each backup live relative to what it protects, and can a backup outage stop normal writes? |
| LC-16 | The recovery root (the key that unlocks storage or the secret store) MUST be external to, or at a lower level than, what it unlocks. It is never stored only inside the encrypted authority it unlocks. | NIST SP 800-53 Rev. 5 SC-12 | After total loss of the installation, which key outside it restores access? |
| LC-17 | A wait MUST be on the owner's native terminal primitive, without polling. Descendants follow by the reconciler's dependency order or native readiness. We store no parallel readiness receipt. | Convention: native wait, no polling | For each wait, which native primitive ends it, and is any readiness copy kept by us? |
| LC-18 | On failure a step MUST close admission, keep the failure evidence, unwind only the handles the failed attempt itself acquired, in reverse order, and leave durable authorities intact. | Convention: unwind only own acquisitions | What does each failure path undo, and can it touch a handle it did not acquire or a durable authority? |
| LC-19 | Shutdown order is: close L4 admission, terminalize or drain L5, verify no borrowing descendant remains, stop L4, flush and stop L2, release L1 runtime handles. | Twelve-Factor App IX (graceful shutdown); Convention: level-ordered shutdown | Does the stop sequence follow this order? |
| LC-20 | A reset or destruction MUST resolve the exact L0 instance and its L6 disposition graph, apply legal-hold and retention guards, require confirmation, invoke only the native deletion owners, and preserve immutable receipts. | Convention: guarded reset by disposition graph | How does a reset prove which instance it acts on, and which native owner performs each deletion? |
| LC-21 | Recovery after a crash, SIGKILL, timeout or host reboot MUST reread the native owner's state and its lease or fencing generation before acting. It never assumes the interrupted effect failed. Missing evidence blocks any destructive recovery. A process tolerates sudden death and starts again without manual cleanup. | Twelve-Factor App IX Disposability | After a kill at each step, what is reread before the next action? |
| LC-22 | A durable authority that exists but does not match its expected generation, pair or format at start is `conflicted`: the consumer stops and alerts. It never initializes the authority empty and never silently adopts it. | Convention: conflicted authority never adopted | What happens when a store exists but does not match what the consumer expects? |
| LC-23 | When a parent is removed or replaced: child admission closes, the exact pinned children drain, and each is migrated, rebuilt or marked conflicted by its state class. A parent change re-drives every dependent effect through the parent's event. | Convention: parent replacement re-drives children | For each parent that can be replaced, which event re-drives its children? |
| LC-24 | A schema or plugin migration MUST follow a backup, use the owner's native migration, be reread by the application, and keep rollback or disposition evidence. A major or incompatible format change is a restore or a new generation beside the old (blue/green), the old kept until the new generation passed its acceptance on real traffic. | Convention: backup-first native migration | Does each upgrade name its backup, native migration and rollback? |
| LC-25 | Compatibility is exact by default. A version range or a mixed-version edge is allowed only after a real compatibility, migration, rollback and failure-injection gate added that exact range. | Convention: exact compatibility until gated | Does the design assume two versions work together without a gate that proved it? |
| LC-26 | Each fact MUST have exactly one semantic owner that holds it. A message, cache, manifest, dashboard, index or record of ours is derived and rebuildable; it is never edited or read as the truth. | Convention: one semantic owner per fact | For each fact the design introduces or moves, who is its one owner, and is a second copy ever read as truth? |
| LC-27 | A missing parent is a state and a dependency failure is a failure class. Neither is ever reported as a business result ("no data", "0 differences", a refusal). | Convention: dependency failure is not business result | Can an absent or failing dependency surface as an empty or business answer? |
| LC-28 | A lifecycle, backup or migration operation that is not an HTTP request creates one correlation root at its L0 entry, before acquiring L1 descendants. Retries keep that root and the idempotency identity and receive new native attempt ids. Recovery adds a successor edge; it never overwrites the failure. | Convention: correlation root per operation | Does each run have one root id from entry, kept across retries, with failures preserved? |
| LC-29 | An operations view and a release verdict read the reconciler's status and each owner's native status directly: the applied revision, native readiness or failure, native parent relation. Neither renders or trusts a copied lifecycle catalog or readiness receipt; static catalog equality is not lifecycle proof. | Convention: read owner status, not copies | Does any status surface or verdict read a copy instead of the owner's status? |
| LC-30 | One-time commissioning (the first administrator) prepares the account, issues the owner's native enrollment and retires its temporary authority without waiting for the person. An independent recovery path MUST exist before that retirement. Commissioning access never counts as full readiness. An ordinary restart preserves people and revocations and never replays setup. No parallel enrollment store is added. | Convention: one-time commissioning with recovery | Is temporary authority retired before a recovery path exists, does an install block on a person, or does a restart re-run setup? |
| LC-31 | The ingress creates one untrusted W3C trace root per public request; it stays unchanged through the operation and each owner adds its own child id. Where the owner supports transactional publication, a durable commit records the root and its native id in the same transaction. Events carry references only. | W3C Trace Context (traceparent); Convention: events carry references only | Is the correlation root replaced mid-operation, or recorded outside the owner's commit? |
| LC-32 | A node's binding digest covers its parent bindings and its contract, configuration, schema or migration, image, chart or plugin, storage format or class, policy and tenant-layout revisions; a change in any of them dirties it. A policy or tenant-layout change reauthorizes future operations and preserves the historical decision revision and data identity. | Convention: binding digest covers all inputs | Which input of a node can change without dirtying it? |
| LC-33 | Each persistent service has a versioned state capsule naming owner and class, native format or schema, exact image digest, effective path, migration and backup authority, compatibility and parent generation. Start rejects a missing, stale or incompatible capsule. When a parent is replaced, each child generation is retained, migrated, archived or disposed through its owner. | Convention: versioned state capsule | What does a consumer do at start with a stale or missing capsule? |
| LC-34 | Proof that an effect happened, or that something exists, is the owner's record or native receipt read back. A file marker or flag of ours is never completion, and a re-run is a no-op on the owner's natural key. | Enterprise Integration Patterns: Idempotent Receiver; Convention: owner receipt read back | Does anything treat a file or flag of ours as completion? |
| LC-35 | A value one host publishes for another flows in one declared direction, through a store that outlives the consumer, and the consumer reads it with its own identity. A consumer reads it only in a step ordered after the step that produces it. | Convention: dependency-ordered provisioning (producer step precedes consumer step) | Does any value travel against the declared direction, or get read before it is produced? |
| LC-36 | Every lineage chain a design touches (who decided, what effect, which data, which software, which policy, which cost, which recovery) ends at the owner's native ids or at a named boundary. Causality is never inferred from a timestamp, a filename, checksum similarity or matching text; no link of a chain is left null, omitted or to implementer judgement: it holds a native immutable id or an explicit not-applicable with a closed reason. The software chain's signature, SBOM and vulnerability decision are links of it: each exists or is a named boundary. | W3C PROV model; NIST SP 800-53 Rev. 5 SR-4 | For each chain the design touches, where does it end, and is any edge inferred or missing? |
| LC-37 | A correlation or lineage index stores ids and relations only (no payload, secret, token, signed URL or unbounded owner document) and never creates an edge no owner recorded. | W3C PROV model; Convention: ids and relations only | What does the index store, and can it create an edge no owner recorded? |
| LC-38 | A stored source's class pairs only with its own kind: an authority with authority, immutable artifact or evidence; a projection with a projection or cache; an ephemeral attempt with an ephemeral one. Any other pairing is rejected. | Convention: state class and authority class pairing | Does each stored source carry a permitted class pair? |
