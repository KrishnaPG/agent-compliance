# SC: Supply chain

Base catalog 1.0.0. Scope: build once, digests, signing, verification, admission, provenance, pinned dependencies. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| SC-01 | A first-party image is built once per input digest, on the release node, and that digest is promoted to every installation. A runtime host never builds; no stage or class rebuilds. | Twelve-Factor App V | Where is each artifact built, and is the same digest promoted everywhere? |
| SC-02 | Every image and artifact is referenced by digest, the digest coming only from the one manifest. A tag beside a digest is allowed and ignored; a tag or mutable name alone is never a reference. | SLSA v1.0 | Is any image, chart or volume referenced by a tag or mutable name alone? |
| SC-03 | There is one artifact declaration and one list of digests. A first-party reference is written only through the manifest-reading reference, so a key outside the manifest fails the render; nothing else caches, copies or supplies a digest. | SLSA v1.0 | Where does each digest come from, and is it written twice? |
| SC-04 | Each artifact is signed with the release's key, held in a managed key service, and its signature carries the source commit and the digest of its build inputs. | SLSA v1.0 | What is signed, by which key, with which annotations? |
| SC-05 | Signature verification (the digest equal to the manifest's, the registry serving that digest) precedes every push and use; a failure fails the release closed and deletes nothing. | SLSA v1.0 "Verifying artifacts"; NIST SP 800-53 Rev. 5 SI-7 | What happens to a release when one signature does not verify? |
| SC-06 | The canonical registry holds the only authoritative copy of each signed digest. Node stores, placement registries and layer caches are rebuildable copies that never authorize deployment; a cache is never trusted for provenance, and a base-digest or build-tool version change forces a cold build. | SLSA v1.0 | Does any decision trust a cache or copy as the source? |
| SC-07 | Registry reads and writes are audit-logged, and a denied pull or push raises an alert that reaches the incident path. | CIS GCP Foundation v4.0.0 2.1; NIST SP 800-53 Rev. 5 SI-4 | What records and reports a denied registry call? |
| SC-08 | OSS versions and digests are pinned exactly; a third-party binary is pinned by version and checksum; each release-node tool is a catalogued entry pinned by digest. | SLSA v1.0 | Is anything fetched by a floating version or without a checksum? |
| SC-09 | A third-party tool, operator, chart, library or image is vetted from its pinned source before adoption, and the vetting is recorded. | SLSA v1.0 | Does the design name a tool with no vetting record? |
| SC-10 | For every deployed digest, its source commit and build inputs are retrievable from the artifact's own metadata. | SLSA v1.0 Build L1; NIST SP 800-53 Rev. 5 SR-4 | Given a running digest, how is its commit and input set found? |
| SC-11 | Build inputs equal the pinned commit: code is committed before its digest is pinned, pinning refuses a dirty tree, a check recomputes every input digest and refuses a mismatch, and no release runs at a commit whose manifest is stale. | SLSA v1.0 | Can a release ship bytes that differ from its commit? |
| SC-12 | The admission webhook stays available and cannot lock out its own repair: at least 2 replicas with a disruption budget, and the system namespaces and its own namespace excluded. | SLSA v1.0 | Can a webhook outage block the controllers that restore it, or all first-party pods? |
| SC-13 | The image path has no script or route of ours that copies, retries or verifies image bytes; only the build, registry, signing and runtime tools, each release step a typed step with a required outcome. | SLSA v1.0 | Does any script of ours handle image bytes? |
| SC-14 | Admission refuses, failing closed, a first-party artifact without a valid release signature; no first-party workload is admitted before the policy exists; any rejection is an incident with an alert. | SLSA v1.0 "Verifying artifacts"; NIST SP 800-53 Rev. 5 SI-7 | Can a first-party workload start before, or without, the signature check? |
| SC-15 | Every artifact digest an installation references, and every digest inside the stated rollback horizon, is retained by the registry's own keep policy; no prune step of ours removes one. | SLSA v1.0; NIST SP 800-53 Rev. 5 CM-2(3) | Can a digest still referenced, or needed for a rollback inside the horizon, be removed? |
