# SC: Supply chain

Base catalog 1.1.0. Scope: build once, digests, signing, verification, admission, provenance, pinned dependencies. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| SC-01 | A first-party image is built once per input digest, on the one designated build-and-release host (the release node), and that digest is promoted to every installation. A runtime host never builds; no stage or class rebuilds. | Twelve-Factor App V | Where is each artifact built, and is the same digest promoted everywhere? |
| SC-02 | Every image, artifact and registry-hosted image volume is referenced by digest, the digest coming only from the one manifest, and an admission policy enforces it. A tag beside a digest is allowed and ignored; a tag or mutable name alone is never a reference. | SLSA v1.0 | Is any image, chart or volume referenced by a tag or mutable name alone? |
| SC-03 | There is one artifact declaration and one list of digests. A first-party reference is written only by a lookup into the manifest, so a name absent from the manifest fails the build of the deployable configuration; nothing else caches, copies or supplies a digest. | Convention: one digest manifest | Where does each digest come from, and is it written twice? |
| SC-04 | Each artifact is signed with the release's key, held in a managed key service, and its signature carries the source commit and the digest of its build inputs. | SLSA v1.0 | What is signed, by which key, with which annotations? |
| SC-05 | Signature verification (against each key in the key set, the digest equal to the manifest's, the registry serving that digest) precedes every push and use; a failure fails the release closed and deletes nothing. | SLSA v1.0 "Verifying artifacts"; NIST SP 800-53 Rev. 5 SI-7 | What happens to a release when one signature does not verify? |
| SC-06 | The canonical registry holds the only authoritative copy of each signed digest. Node stores, regional or pull-through registries and layer caches are rebuildable copies that never authorize deployment; a cache is never trusted for provenance, and a base-digest or build-tool version change forces a cold build. A registry is chosen only if it natively provides digest immutability, access control, keep policies and durability. The canonical registry is an L2 authority with its own backup (DS-03), or every retained digest is rebuildable from its pinned commit and re-signed. | Convention: caches never authorize deployment | Does any decision trust a cache or copy as the source? |
| SC-07 | Registry reads and writes are audit-logged, and a denied pull or push raises an alert that reaches the incident path. | NIST SP 800-53 Rev. 5 AU-2, AU-12, SI-4 | What records and reports a denied registry call? |
| SC-08 | OSS versions and digests are pinned exactly; a third-party binary is pinned by version and checksum; each tool the build-and-release host runs is a catalogued entry pinned by digest. | Convention: exact version and checksum pinning | Is anything fetched by a floating version or without a checksum? |
| SC-09 | A third-party tool, operator, chart, library or image is vetted from its pinned source before adoption, and the vetting is recorded. | Convention: vetting record before adoption | Does the design name a tool with no vetting record? |
| SC-10 | For every deployed digest, its source commit and build inputs are retrievable from the artifact's own metadata. | SLSA v1.0 Build L1; NIST SP 800-53 Rev. 5 SR-4 | Given a running digest, how is its commit and input set found? |
| SC-11 | Build inputs equal the pinned commit: code is committed before its digest is pinned, pinning refuses a dirty tree, a check recomputes every input digest and refuses a mismatch, and no release runs at a commit whose manifest is stale. | SLSA v1.0 | Can a release ship bytes that differ from its commit? |
| SC-12 | The admission control stays available and cannot lock out its own repair: it runs redundantly (at least 2 instances, at least 1 always available during maintenance), and the platform's system scope, the scope of the controllers that restore it, and its own scope are exempt from it. | Convention: admission control self-repair | Can an outage of the admission control block the controllers that restore it, or all first-party workloads? |
| SC-13 | The image path has no script or route of ours that copies, retries or verifies image bytes; only the build, registry, signing and runtime tools, each release step a typed step with a required outcome. | Convention: no custom handling of image bytes | Does any script of ours handle image bytes? |
| SC-14 | Admission refuses, failing closed, a first-party artifact without a valid release signature; no first-party workload is admitted before the policy exists; any rejection is an incident with an alert. | SLSA "Verifying artifacts"; NIST SP 800-53 Rev. 5 SI-7 | Can a first-party workload start before, or without, the signature check? |
| SC-15 | Every artifact digest an installation references, and every digest inside the stated rollback horizon, is retained by the registry's own keep policy; no prune step of ours removes one. | NIST SP 800-53 Rev. 5 CM-2(3) | Can a digest still referenced, or needed for a rollback inside the horizon, be removed? |
| SC-16 | A design claims a build-provenance level, an SBOM, a vulnerability decision or build isolation only if it exists; one that needs a missing one names the boundary. Signing and verifying use separate duty identities. | SLSA v1.0; NIST SP 800-53 Rev. 5 SR-4, SI-7 | Does the design claim provenance, SBOM, scanning or build isolation that does not exist? |
| SC-17 | A build-cache or lookup entry is written only after the artifact is pushed and signed, so an interrupted build leaves no usable entry; build timestamps come from the source commit; a failed lookup runs the build and a repeated failure of the same cause fails closed. | Convention: sign before publishing a lookup entry | Can an unsigned or partial artifact be found by lookup? |
| SC-18 | The recovery from loss of the signing key, the canonical registry and a derived registry is stated: key rotation with re-signing or rebuild, rebuild into new digests, or re-push of the same content. | NIST SP 800-53 Rev. 5 CP-9, SC-12 | What is the recovery from losing the key or the registry? |
| SC-19 | Content built by an untrusted party never enters the trusted release registry and never uses the release's build tools. | Convention: trusted and untrusted build paths stay apart | Can untrusted content reach the release registry or its build tools? |
| SC-20 | A stuck or slow image pull alerts against a stated bound, and no runtime no-progress timeout is overridden. | Convention: bounded, alerted image pulls | What alerts on a failed or slow pull, and is any pull unbounded? |
