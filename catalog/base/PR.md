# PR: Process

Base catalog 1.0.0. Scope: defect records, independent review, forward-only history, tests kept strict. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| PR-01 | A defect of any size gets a record with its root cause and a test that reproduces or guards it; its fix references the record. The record closes only when that test passes on the fixed product, and a later failure reopens it. | Google SRE book ch. 15 (postmortems) | What does the artifact say to do when a defect is found during the work, and when does its record close? |
| PR-02 | A test is written only for what no dashboard, log, platform status, check or release smoke would show: racy or edge-case decision logic, absence invariants, money and entitlement arithmetic, transformation programs on fixtures, cross-service schemas, the order of irreversible steps. Never a test that searches source text or repeats an outcome a release shows. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | What does each proposed test catch that nothing else shows? |
| PR-03 | Pushed history is never rewritten and the main branch is never force-pushed; a commit refused after it was pushed is corrected by a later commit that names it. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | Does any step rewrite or force-push history? |
| PR-04 | The review is by a reviewer who did not write the artifact and shares no context with its author, given the artifact without the author's reasoning; it names a location and a fix for each finding. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | Who reviews, and what is the reviewer given? |
| PR-05 | The owner's validator (server dry-run, chart template with merged values, rule checker, template render) runs on changed files before commit and is named in the commit. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | Which validator covers each changed file? |
| PR-06 | People's and agents' own waits follow RL-08: no sleep or poll loop in a shell; a wait is on the producer's event or a background task's completion. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | Does any instruction tell a person or agent to sleep or poll? |
| PR-07 | The standards win over a brief or an older artifact. A gate's refusal means the change broke a rule and is answered by a design step back, never a bypass. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | What does the process do when a gate refuses? |
| PR-08 | No existing acceptance test is changed, loosened, skipped, re-timed or re-seeded to make it pass; a failing acceptance test is a product defect. Exception: the native owner's source proves no correct product can pass it as written, or a later approved decision settles which of two contradicting tests is stale; then only that defect is corrected, every assertion stays as strict, and the proof is recorded on the defect. | Google SRE book ch. 15 (postmortem culture); trunk-based delivery practice | Does the work edit an existing acceptance test, and under which exception? |
| PR-09 | Every confirmed review or audit finding is recorded on its tracker in the same turn it is found; none stays in prose. | Code review practice (Google engineering practices) | Where does each finding go, and when? |
| PR-10 | Only decisions that are the owner's to make are escalated (a conflict between approved documents, a new owner, a wider privilege, retention, scope), each named as such. Anything else is decided by the standard and recorded. An escalation never stops the work. | Decision-rights practice (RACI) | Is each open question the owner's to decide, and does work continue around it? |
