# DS: Data safety and retention

Base catalog 1.0.0. Scope: no deletion without backup or decision, recovery tiers, deletion eligibility, projections, erasure. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| DS-01 | No data-bearing object (volume, database, bucket, stream, storage pool, generated-once secret, host data directory) is deleted by a person, agent, job, prune or configuration state unless (a) a completed native backup newer than its last write exists, within its tier's RPO (DS-12), whose restore passed, or (b) a recorded owner decision says it is not retained. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | For each deletion in the design: which backup or which decision authorizes it? |
| DS-02 | Authorities of one capsule (an application's files and its database) move together, child-first; one of a pair is never deleted alone. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Does any step remove part of a paired authority? |
| DS-03 | Each L2 authority has a scheduled native backup whose interval meets its tier's RPO (DS-12), an alert when the newest backup is older than the RPO, and a restore drill into an isolated target; a backup with no passed restore does not count. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | For each new or changed authority: its backup, its staleness alert, its restore drill? |
| DS-04 | Deletion walks the reverse reference graph. A record is eligible only when its semantic owner permits it, no retained descendant or active share needs it, no legal hold exists, retention expired, the backup policy permits disposition, and the exact generation and fingerprint reread still match. It leaves an immutable tombstone or receipt, never deletes the lineage node, and never lets old evidence claim the bytes still exist. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | What is checked immediately before each delete, and what remains after? |
| DS-05 | A rebuildable projection (cache, baseline, telemetry store, runner cache, index, backup working set) declares its retained source, replay horizon, rebuild path, retention and disposition, and never authorizes deployment. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Does any cache or baseline decide whether something deploys? |
| DS-06 | A missing owner guarantee is never repaired with custom service code, DTOs, code hooks, SQL triggers or managed-cloud-only storage; the owner or profile is marked unavailable and the architecture fixed. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Where the owner lacks a guarantee, does the design add glue or name the boundary? |
| DS-07 | A seed, migrate, clean or reset is explicit, idempotent, scoped to an installation, and prints its target before mutation. A clean deletes only generated, run-scoped state; a durable reset names its target and needs explicit confirmation. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | What does each destructive command print and require before it acts? |
| DS-08 | Automation that can destroy data-bearing objects at scale is limited or confirmed so a person can intervene before the loss is total. | Release It! 2nd ed. Governor | How many data-bearing objects can one automated run delete before anyone can stop it? |
| DS-09 | Only a fresh install and a restore from backup are supported recoveries; data lost with no restore is a fresh install. A restore re-drives the reconciliations of what it restored (until wired, the audited operator re-drive). No sweep or catch-up job exists for a lost-data incident. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | After a restore, what brings dependents back in line, and does the design add a sweep for lost data? |
| DS-10 | A failed step leaves durable authorities intact and recovery rolls forward by the next digest; nothing compensates by deletion. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Does any failure path delete data to get clean? |
| DS-11 | A test never writes state its owner produces, nor asserts a value copied from the owner that derives it. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Does any test create or hard-code an owner's state? |
| DS-12 | Each capsule declares its recovery tier, and its backup and restore meet the tier's maximum RPO and RTO: T0 5 min and 30 min (continuous log archiving with point-in-time recovery, encrypted offsite copy, quarterly restore); T1 15 min and 4 h; T2 1 h and 8 h; T3 none (a rebuild target with bounded cleanup). A profile may tighten a tier, never silently weaken it; a single-node profile states that node loss exceeds T0 and T1. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Which tier is each new store, and does its backup interval, offsite copy and restore time meet it? |
| DS-13 | Deletion is never inferred from a cancellation. A destructive mutation previews its impact and preserves rollback, export and retention evidence. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Can a cancelled order, subscription or run delete data? |
| DS-14 | Receipts and fingerprints are never fabricated: each is read from the owner. | NIST SP 800-53 Rev. 5 CP-9, CP-10, SI-12 | Is any receipt, digest or fingerprint written by us instead of read from the owner? |
| DS-15 | An erasure states each copy's fate: the owner's delete confirmed by event; projections rebuilt without the subject; telemetry holding no personal data; backups expiring within their stated retention; one receipt per owner. | GDPR Art. 17; NIST SP 800-53 Rev. 5 SI-12 | For each copy of the erased data (owner, projection, telemetry, backup): what removes it, by when? |
| DS-16 | Retirement is a state of the record, in two steps: first drain (children removed), then destroy compute only; data, network and keys are protected from destroy until an approved disposition. | NIST SP 800-53 Rev. 5 SI-12, MP-6 | What does each retirement step destroy, and what stops it destroying more? |
