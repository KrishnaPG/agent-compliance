# NO: Native owners and least code

Base catalog 1.0.0. Scope: use the owner directly, OSS before code, lowest native rung, delete replaced wiring, no over-engineering. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| NO-01 | The owner's native file, client or API is used directly; nothing wraps it. A binding is verified by a real development call and the owner's response or read-back. | Reuse-before-build practice | Is there a layer between the design and the owner's own file, client or API? |
| NO-02 | A repository type, field, block, catalog, check or gate exists only for a value the native call consumes or a failure no owner, engine, admission or release smoke catches; otherwise it is deleted. No wrapper, DTO, marshaller, intermediate language, compiler, copied flag catalog, re-encoded native file, coverage matrix, or validator repeating the owner's. | Reuse-before-build practice | For each new piece of machinery: which native call consumes it, or which uncaught failure does it catch? |
| NO-03 | Engine configuration is the engine's native file, validated by the engine. No second language re-encodes it; a renderer supplies only installation-specific values it consumes. | Reuse-before-build practice | Is any native configuration expressed through a second language? |
| NO-04 | An owner-client call passes only arguments documented at the pinned version. | Reuse-before-build practice | Is each flag and argument in the owner's documentation at the pinned version? |
| NO-05 | Before code is written for a capability, an OSS tool that provides it is searched for, vetted and adopted when it passes; native configuration, standards, CLIs and SQL are exhausted first. Our code is integration and orchestration only, never a rebuild of what an OSS owner does. | Reuse-before-build practice | Which OSS owner was checked for each capability the design builds? |
| NO-06 | Work inside an adopted owner takes the lowest rung that does it: 0 delete (the owner already does it or nobody needs it); 1 a declarative artifact the owner applies itself; 2 the owner's own CLI or importer on a file (one command); 3 one call of the owner's public function or API. Never rung 4 (our code in the owner's extension point) or rung 5 (our program sequencing several owner calls to apply configuration or seed data). Exception to rung 4: a documented extension point may carry minimal code that obtains a credential its own client sends, never moving business data. | Reuse-before-build practice | Which rung is each change, and is a lower one possible? |
| NO-07 | A native behaviour the design relies on is proven from the owner's pinned source (path and line at the pinned tag), once per fact and tag; a documentation page alone is unknown. A tag bump re-verifies only the cited locations. An owner used for the first time gets a table of its native facts from its pinned source. | Reuse-before-build practice | Which pinned source location proves each claimed native behaviour? |
| NO-08 | An inline program (`sh -c`, `python -c`, `node -e`, a heredoc) is not a rung and is never added. | Reuse-before-build practice | Does the design add inline shell or script anywhere? |
| NO-09 | The repository adds no custom runtime or service code, executable, startup controller, discovery or health service, daemon, wrapper type, code hook inside an owner, database trigger, retry loop or glue. An unavailable native guarantee blocks the profile and the architecture is reworked. | Reuse-before-build practice | What new program or daemon does the design introduce? |
| NO-10 | A toolchain (version control, task runner, build tools) follows conventional practice and is never modelled as an owner. Repository tooling never becomes a second control plane: it keeps no orchestration state and decides nothing its owners decide. | Reuse-before-build practice | Does the tooling keep state, sequence owners or decide what the owners decide? |
| NO-11 | A block that replaces an older path deletes the replaced wiring in the same change, after equivalent real-flow qualification; competing implementations never coexist. | Reuse-before-build practice | What does the design delete, and do old and new run side by side? |
| NO-12 | A defect is fixed in the native file, binding or shared block that owns it, after tracing its users; never by a per-instance patch, a fallback or a widened timeout. | Reuse-before-build practice | Is any fix applied at a symptom site instead of the owner? |
| NO-13 | The design starts from an inventory of what already exists (path and guarantee); each proposal is KEEP, MOVE to the native owner (deleting the old), or NEW for a verified gap only. | Reuse-before-build practice | What existing implementation covers each proposed item? |
| NO-14 | A mechanism the design makes obsolete or finds unused is deleted by it, verified from references and callers; it is not kept beside the new one nor raised as a question. | Reuse-before-build practice | What is on the delete list, and is anything dead left in place? |
| NO-15 | No over-engineering: the least complex profile that meets the stated loss, freshness, recovery and retention budgets. No durable queue, DLQ, saga, replicated store, circuit breaker or framework without a stated requirement. | Reuse-before-build practice | Which stated requirement needs each mechanism? |
| NO-16 | SQL against an owner's database is a named program of that database (a report, a view), run by the owner's engine. | Reuse-before-build practice | Does any SQL run from our scripts instead of the owner's engine? |
| NO-17 | Authority order: approved specifications and decisions outrank the verifier (gate, check, test), and the verifier outranks the producer (generator, task, seed, product code). A producer emits only what its verifier accepts, by calling the verifier's own code; a verifier weaker or stricter than its text is corrected to the text. | Reuse-before-build practice | Do a generator and its checker share one implementation of the rule? |
| NO-18 | Owner configuration is the owner's native record, applied by the owner's own mechanism and validated by the owner; our admission never repeats the owner's validation. | Reuse-before-build practice | Who validates each configuration, and is it validated twice? |
| NO-19 | A new shared block names the cross-owner guarantee it adds and the pinned pattern or engine feature it uses, stays small enough to read in full, and is reviewed independently before it is written. | Reuse-before-build practice | Is each new block's guarantee, pattern and review named? |
| NO-20 | No fact, graph, list or order is declared in two places. | Reuse-before-build practice | What is written twice, and which copy would be believed? |
| NO-21 | Each tool does one job, takes its inputs by file, standard input or API only, gives deterministic output and exits nonzero on any failure. No new monolithic control plane. | Reuse-before-build practice | Is each tool one job with a defined exit code? |
| NO-22 | Responsibility is never relocated between owners and a replaced design is never revived. A change that conflicts with an approved decision needs the owner's authorization and the decision updated first. | Reuse-before-build practice | Does the design move a duty or bring back a retired mechanism? |
| NO-23 | A UI edit passes the same admission path as a file edit. Hand-edited generated output, and a baseline edited to silence a gate, are rejected. No second DSL, runtime catalog or interpreter is added. | Reuse-before-build practice | Can an admin UI change bypass the check a file change gets? |
| NO-24 | A template or binding change names its affected instances, compatibility, real-flow evidence and cutover and rollback. | Reuse-before-build practice | Which instances does each template change reach? |
| NO-25 | Every user and consumer of a changed or removed interface is traced and updated in the same change: no lost behaviour and no missed consumer. | Reuse-before-build practice | Which consumers read what the design changes, and is each updated? |
| NO-26 | Legacy only shrinks: a file inventoried as legacy only loses functionality, is deleted or is replaced by its native form; a new duty is written natively, never added beside a wrapper. | Strangler Fig pattern (Fowler) | Does the design add to a legacy-listed file? |
