# DC: Documents

Base catalog 1.0.0. Scope: current-rule documents, one home per rule, conflicts named, no assumed capability. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| DC-01 | Every line of a document an agent or engineer reads (instructions, standards, decision records, specifications, plans) is correct and actionable for a reader who loads only that line, section or file. | Single-source-of-truth documentation practice | Read each section alone: is anything wrong or unusable without another section? |
| DC-02 | A decision rewrites, in the same change, every line in every document that states the old rule. | Single-source-of-truth documentation practice | Which other documents state what this artifact changes, and are they in the change? |
| DC-03 | No document carries replacement wording, a dated amendment beside the old text, a revision history, change markers, or an appendix mapping old rules to new ones. Provenance goes in the commit message and the tracking issue. | Single-source-of-truth documentation practice | Does the artifact describe its own history instead of the current rule? |
| DC-04 | A document that no longer governs anything is deleted. Evidence annexes (inventories, measurements) stay. | Single-source-of-truth documentation practice | Does the change leave a document that governs nothing? |
| DC-05 | The design applies every relevant requirement of the project's glossary, context documents, decision records and approved specifications, failure cases included, and never asks the owner to reselect an approved decision. | Single-source-of-truth documentation practice | Which approved requirement in scope does the artifact not address? |
| DC-06 | The design records only a named cross-owner guarantee or an unavailable native boundary. A table of clauses or coverage is never offered as proof that a native capability works; the proof is the real call. | Single-source-of-truth documentation practice | Does the artifact offer a table as proof where a real call is the proof? |
| DC-07 | A design never rewrites the standards to fit itself. Where the standards cannot express the brief, the gap is stated separately, reviewed alone, and the design waits. | Single-source-of-truth documentation practice | Does the change edit a standard it is judged by? |
| DC-08 | A conflict between approved documents, or between an industry standard and an approved decision, goes to the owner with both clauses quoted; it is never designed around. | Single-source-of-truth documentation practice | Where two sources disagree, is the conflict named or silently resolved? |
| DC-09 | Skills, memory, hand-offs and older artifacts never override an approved Spec. An explicit owner override is honoured and its exact scope recorded. | Single-source-of-truth documentation practice | Does the artifact rely on an unrecorded instruction against an approved text? |
| DC-10 | A rule has one home; other documents link the existing contract instead of copying it. (This catalog's rows are the review's working text; the source stays the rule's home.) | Single-source-of-truth documentation practice | Is any rule or contract restated in the artifact that lives elsewhere? |
| DC-11 | A missing capability or decision is a named blocked gate; never assumed support, a fabricated placeholder or aspirational prose. | Single-source-of-truth documentation practice | What does the artifact assume exists that nothing has proved? |
| DC-12 | A generic claim ("improve reliability", "make it observable") is invalid without its named owner, template, contract, file or flow stage. | Single-source-of-truth documentation practice | Which claim names no owner or file? |
