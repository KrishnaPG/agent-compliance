# DC: Documents

Base catalog 1.0.0. Scope: current-rule documents, one home per rule, conflicts named, no assumed capability. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| DC-01 | Every line of a document an agent or engineer reads (instructions, standards, decision records, specifications, plans) is correct and actionable for a reader who loads only that line, section or file. | Convention: each line stands alone | Read each section alone: is anything wrong or unusable without another section? |
| DC-02 | A decision rewrites, in the same change, every line in every document that states the old rule. | Single-source-of-truth documentation practice | Which other documents state what this artifact changes, and are they in the change? |
| DC-03 | No document carries wording that marks a rule as superseded, withdrawn, replaced or amended by another (such as "supersedes", "superseded by", "withdrawn", "amended by"), a dated amendment beside the old text, a revision history, change markers, or an appendix mapping old rules or review items to new ones. Provenance goes in the commit message and the tracking issue. | Convention: documents state current rule | Does the artifact describe its own history instead of the current rule? |
| DC-04 | A document that no longer governs anything is deleted. Evidence annexes (inventories, measurements) stay. | Convention: delete ungoverning documents | Does the change leave a document that governs nothing? |
| DC-05 | The design applies every relevant requirement of the project's glossary, context documents, decision records and approved specifications, failure cases included, through the owner's native file or call, and never asks the project owner to reselect an approved decision. | Convention: apply approved requirements | Which approved requirement in scope does the artifact not address? |
| DC-06 | The design records only a named cross-owner guarantee or an unavailable native boundary. It carries no clause matrix, no catalog of owner functions and no static coverage table; static traceability never qualifies a native capability, the real call does. | Convention: real call is the proof | Does the artifact carry a clause matrix, an owner-function catalog or a coverage table, or offer one as proof? |
| DC-07 | A design never rewrites the standards to fit itself. Where the standards cannot express the brief, the gap is stated separately, reviewed alone, and the design waits. | Convention: design never edits its standard | Does the change edit a standard it is judged by? |
| DC-08 | A conflict between approved documents, or between an industry standard and an approved decision, goes to the project owner with both clauses quoted; it is never designed around. | Convention: conflicts go to owner | Where two sources disagree, is the conflict named or silently resolved? |
| DC-09 | Agent instructions, notes, hand-off documents and older artifacts never override an approved specification. An explicit override by the project owner is honoured and its exact scope recorded. | Convention: approved text outranks memory | Does the artifact rely on an unrecorded instruction against an approved text? |
| DC-10 | A rule has one home; other documents link the existing contract instead of copying it. (This catalog's rows are the review's working text; the source stays the rule's home.) | Single-source-of-truth documentation practice | Is any rule or contract restated in the artifact that lives elsewhere? |
| DC-11 | A missing capability or decision is a named blocked gate; never assumed support, a fabricated placeholder or aspirational prose. | Convention: missing capability is blocked gate | What does the artifact assume exists that nothing has proved? |
| DC-12 | A generic claim ("improve reliability", "make it observable") is invalid without its named owner, template, contract, file or flow stage. | Convention: claims name their owner | Which claim names no owner or file? |
