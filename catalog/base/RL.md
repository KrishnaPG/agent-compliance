# RL: Reliability and recovery

Base catalog 1.1.0. Scope: detect, remediate, verify, escalate; deadlines; no timers; idempotent re-runs; rollback; unattended runs. Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| RL-01 | The artifact MUST state, for each failure it can cause or meet, how the failure is detected, remediated through its owner, verified, escalated until fixed, and what prevents data loss, each by the artifact that makes it true (the alert rule, its test, the runbook, the backup object, the admission policy, or a real call: an alert that fired and resolved, a passed restore, a from-scratch run). | Convention: five-step failure statement per failure | Is there a failure with a missing step, or a step backed only by a citation? |
| RL-02 | Each alert rule of ours states how long the condition must hold, has a test that fires it on a fixture, and, when its selector reads series that can vanish, has a companion absence rule of the same severity, so a selector that matches nothing is a failure, not silence. | Convention: alert hold time and absence rule | For each new rule: its hold time, its test, and what fires when its selector matches nothing? |
| RL-03 | A remediation takes the lowest native rung that does it (delete, else the owner's declarative artifact, else its CLI, else one API call; NO-06), has one actor and one retry owner with an attempt budget counted from the owner's record, acts only on the labelled installation, and never deletes a data-bearing object. A rule with no automatic remediation escalates at once. | Convention: one remediation actor, one retry owner | Who runs each remediation, how many times, on which installation, and what happens when there is none? |
| RL-04 | A step or fix is done only when the owner's object status reads healthy at the applied revision and its alert resolved while its absence companion is quiet. An exit code, a log line, a statement, a derived series, a dashboard summary or a silence is not verification. | Convention: verify by owner status | What exactly is read to call each step or fix done? |
| RL-05 | A process that reaches a dependency at start waits on that dependency's native readiness. Nothing assumes the network or a peer is usable at t=0. | Convention: wait on dependency readiness at start | For each dependency used at start, what readiness is waited on? |
| RL-06 | Every wait has a deadline whose expiry is a failure the owner's status reports: every job, every reconcile level and every converge-time call carries an explicit timeout. | Release It! 2nd ed. Timeouts | Which wait in the design has no deadline, or a deadline whose expiry nothing reports? |
| RL-07 | Every step, job, managed object, flow and release is idempotent and re-runnable after a crash at any step; every mutation is scoped, observable and resumable. | Enterprise Integration Patterns: Idempotent Receiver; Convention: crash-resumable steps | For each step, what does a second run after a partial first run do? |
| RL-08 | No timer or waiting loop of ours, anywhere (shell, configuration management, service units, manifests, flows, application code): no schedule, cron, timer unit, sleep, poll, requeue or retry override. A wait blocks on the producer's event through the layer's native mechanism; a producer that emits no event gets one. Where no event can exist the case is a named boundary. A business schedule that is itself the requirement (a monthly statement, a retention deadline) is an owner-required periodic field under RL-09, declared with its period key (HO-21), never a repair or delivery path. | Convention: event-driven waits, no timers | Does anything in the design start, repeat or wait by time? |
| RL-09 | An owner-required periodic field (a reconciler's interval, a backup schedule, a retention deadline, certificate renewal, alert evaluation) stays the owner's and is never the repair, delivery or drift-detection path of ours; correctness never depends on its tick. | Convention: owner periodic fields never a repair path | Does correctness depend on any periodic tick? |
| RL-10 | Inputs and preconditions are checked, and every missing or invalid key reported with its expected type and source, before the first effect. | Release It! 2nd ed. Fail Fast | What is validated before the first write, and can a run fail late on an input it could have read first? |
| RL-11 | Everything that accumulates in steady operation (logs, run records, artifacts, worktrees, state and lock files, caches, registry versions, temp files) has an automatic bound or cleanup, so no installation needs a person to purge to keep running; a rebuild target's cleanup is bounded. | Release It! 2nd ed. Steady State | What grows with each run, and what bounds it without a person? |
| RL-12 | One component's failure or slowness MUST NOT amplify into its callers or neighbours: retries are budgeted at one owner (HO-07), deadlines travel with the call (HO-19), and a caller stops pulling, sheds load or applies back pressure instead of queueing without bound. | Google SRE book ch. 22 "Addressing Cascading Failures"; Release It! 2nd ed. Cascading Failures, Shed Load, Create Back Pressure | When one dependency slows or fails, what stops load piling onto it and its callers? |
| RL-13 | An irreversible step never runs before a later step that can still refuse. Where the order of irreversible steps is logic of ours, it has a test. | Convention: irreversible steps last | Which steps cannot be undone, and can anything after them still say no? |
| RL-14 | When a step ends failed or stays pending, the operator sees that terminal state and a repair path exists that is an event or a named re-drive, not only a new commit. | Convention: visible terminal failure with repair path | For each terminal failure, what does the operator see and do? |
| RL-15 | A reconciliation or wait never treats a terminal failed, killed or cancelled state as done and never inspects only a time window. | Convention: failed child never reads as done | Can a failed child or an old failure read as completion? |
| RL-16 | An unattended step never waits for input: no prompt, no terminal, no person's credential on its path. Tools run non-interactively under the step's own identity, one per duty and least-privileged (ID-11). | Convention: unattended steps never prompt | Run with no terminal and no person: where does the design stop and wait? |
| RL-17 | An unattended run ends with one machine-read verdict: its result and a nonzero exit on any failure, never partial success. A failed release alerts and holds every next start (RL-26). Nothing acts between starts when no person is present: that is a named boundary, and a design must not assume an automatic re-run. | Convention: one machine-read verdict per run | What single result does a caller or machine read, can a failed part still exit zero, and does the design assume someone re-runs it? |
| RL-18 | A retry exists only for a failure that provably did not reach the target. | Convention: retry only unreached failures | For each retried call, what proves the first attempt had no effect? |
| RL-19 | A `warning` alert whose lead time can run out (a filling disk, exhausting inodes, an expiring certificate) has a `critical` sibling or a machine reader; a warning nobody reads is not detection. | Convention: warning needs an actor | For each warning the design can raise, what acts on it before it becomes an outage? |
| RL-20 | Each execution ends failed at its own absolute deadline. The repair of a failed end-to-end flow is an audited re-drive (HS-19) or an event-woken reconciliation. | Convention: absolute deadline per execution | What ends an execution that never completes? |
| RL-21 | A conditionally skipped step never leaves a later step reading an output that was not produced: the later step is skipped with it or states what it does when the output is absent. | Convention: skipped step output contract | Which later step reads the output of a step that can be skipped? |
| RL-22 | An upgrade never changes the natural key between the old and the new install path. Replace semantics (a custom permission set replacing the shipped one) never hide rows the owner ships. | Convention: stable natural key across upgrades | Does a migration re-key existing rows, or replace a set that the owner also writes? |
| RL-23 | Each integration profile declares its loss tolerance, its recovery and freshness targets and its bounds. A durable profile selects acknowledgement behaviour, persistence, retry and circuit scope, retention and failed-DLQ behaviour; memory-only or log-only recovery cannot satisfy it. A rebuildable profile references its retained source and rebuild path and omits durability machinery it does not need. | Enterprise Integration Patterns: Guaranteed Delivery, Dead Letter Channel; Convention: declared loss and freshness profile | What loss and freshness does each edge promise, and what implements it? |
| RL-24 | A failure the owner already exposes is read through the owner's aggregated status by one generic rule, plus the monitoring stack's default rules. A rule of ours is added only for a failure no owner status exposes; disabling a default rule requires a rule covering the same failure. | Google SRE book ch. 6 (symptoms over causes) | Does the design add a per-symptom rule where the owner's status already shows the failure, or drop a default without a replacement? |
| RL-25 | Remediation is the owner's own native action or a reviewed, named command, stated in the alert's runbook. It is never a command typed on an installation or a file placed by hand in a managed location; such a command is itself an incident. | Convention: infrastructure as code (a hand change is drift); Google SRE book ch. 14 for incident handling | Does any recovery step need a shell on the installation or a hand edit? |
| RL-26 | A release or push start reads the firing alerts and refuses to start while a critical one fires, except its own alerts and an alert whose time-bounded silence names its defect record. A firing incident is taken before new work, and escalation never depends on an external tracker being reachable. | Convention: release gating on firing alerts; Google SRE book ch. 14 | Does any start path bypass the alert read, or any silence lack its record or bound? |
| RL-27 | A change reaches each installation class in order (development, verification, production). A change to an install path counts as verified only after a run from an empty machine converged it. | Twelve-Factor App X (dev/prod parity); Convention: staged promotion and empty-machine proof | Does the design change an install path, and where is its empty-machine proof planned? |
| RL-28 | A bad release is undone by applying the previous signed release as a new forward apply, within a stated horizon; nothing is deleted to undo it. Schema, data and operator changes are expand-then-contract; an upgrade of a store or its operator follows a backup whose restore passed. A failed step keeps its objects and recovery rolls forward. | Expand-and-contract (parallel change) pattern; NIST SP 800-53 Rev. 5 CP-10 | What is the rollback of each change, and does any step make it impossible? |
| RL-29 | Every incident that stopped a workflow and every data loss has a record that classifies its cause: a failure was not detected, remediated, verified or escalated; or a guard, backup, ordering or install-path rule should have made it impossible; or both. | Google SRE book ch. 15 (postmortems) | Does the design's failure handling end in a record with that class? |
