# HS: Hand-off scenarios

Base catalog 1.1.0. Scope: one row per kind of hand-off (event, command, webhook, bulk transfer, projection, repair, deletion, control plane). Each row is the whole rule; judge it from the row alone.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| HS-01 | A domain event (an owner's committed change others act on) goes by change-data capture or the owner's change stream onto the durable channel and to one durable consumer per target, with explicit acknowledgement, an idempotent effect and a circuit breaker. Owner code never calls targets, and a webhook is never the hand-off. | Enterprise Integration Patterns: Publish-Subscribe Channel, Durable Subscriber, Guaranteed Delivery | How does each committed change reach its consumers? |
| HS-02 | An asynchronous command to another owner uses a work-queue stream with one consumer group; the command id is the idempotency key; the deadline is in the envelope; the outcome returns as an event correlated by `causationid`. Never a request held open across the work, never fire-and-forget without an outcome event. | Enterprise Integration Patterns: Command Message, Correlation Identifier, Competing Consumers | Does each command have a deadline and an outcome event correlated to it? |
| HS-03 | An interactive user command goes synchronously to the owner's API through the ingress, which authenticates the request, with an idempotency key; the owner commits and returns a reference; follow-on work is an event or command. The owner never fans out synchronously to other owners nor returns success before commit. | Convention: commit then publish, interactive command | What does the user-facing call do beyond one owner commit? |
| HS-04 | A synchronous read between services is request-reply to the owner's read API with a deadline, a breaker and a bulkhead, within a stated maximum number of synchronous hops. A cache is allowed only with a version or expiry and the owner remaining the authority, never for authorization without a revision. A synchronous chain that mutates is prohibited. | Enterprise Integration Patterns: Request-Reply; Convention: bounded synchronous hops with deadline, breaker and bulkhead | How many synchronous hops (against the stated maximum), what bounds each, and does any chain write or any cache answer without a version? |
| HS-05 | An inbound webhook is edge ingest onto the durable channel, answering success only after the publish is confirmed. The signature is verified at the edge; the message id is the provider's event id; the provider's own retries cover edge outages; reconciliation against the provider's list API is mandatory. Never processed inline, never an unsigned body trusted, never the only source of truth. | Enterprise Integration Patterns: Channel Adapter | Is the webhook processed inline, unsigned, or trusted as the only source? |
| HS-06 | Browser or device events are captured at the edge onto the durable channel with acknowledgements end to end; identity comes from the authenticated request, never the body; the id is assigned at the edge. The edge never writes stores directly. | Enterprise Integration Patterns: Channel Adapter | Where does captured identity come from, and where does the edge write? |
| HS-07 | An outbound call to an external API runs from a consumer of the durable channel or from an orchestrated step, with a provider idempotency key, query-before-retry, a throttle, a breaker and secrets from the secret store; the result is published as an event with the provider's id. Never from inside an owner's transaction, never retried after a timeout without querying. | Enterprise Integration Patterns: Messaging Gateway; Convention: idempotent, throttled provider call | From where is the provider called, and what makes a repeat safe? |
| HS-08 | A notification to a person is an event, then a route, then the provider: the notification id is the idempotency key, the provider message id is recorded, quiet hours and rate limits apply per recipient, bounces return as inbound webhooks. Never sent inside the owner's transaction; e-mail is never a hand-off between systems. | Convention: notification as event then send | Is any message to a person sent inside an owner transaction, unlimited per recipient, or used as integration? |
| HS-09 | A long-running multi-owner process is an orchestrated flow started by an event or command: one step per owner, a compensation per recorded effect, an approval wait with a timeout and an escalation, the terminal state published as an event. No choreography of ordered effects, no in-memory saga, no sleep loop. | Enterprise Integration Patterns: Process Manager | What coordinates the ordered steps, and what happens when an approval is not given in time? |
| HS-10 | A bulk transfer (export, snapshot, backfill, artifact) writes the object to the object store with a checksum by resumable upload, then publishes the reference event; one manifest per batch; idempotent on object key plus checksum; the consumer verifies size and a cryptographic checksum (SHA-256 or stronger). No large payload on the message channel and no partial object visible to consumers. | Enterprise Integration Patterns: Claim Check | How do bulk bytes move, and when do consumers first see them? |
| HS-11 | Telemetry (metrics, logs, traces, analytics) is declared lossy-bounded and flows collector to backends with persistent queues. It never drives billing, authorization or a business effect and is never a hand-off; a business fact seen in telemetry is re-emitted by its owner as an event. | Convention: telemetry is never a hand-off | Does any decision or effect read a metric, log or trace? |
| HS-12 | A data-plane transfer is a direct, authorized byte transfer under a short-lived native grant, completion signalled by the owner as an event, checksum verified. Bytes are never proxied through application services, and a signed URL is never long-lived. | Convention: direct short-lived data-plane transfer | Which service do the bytes pass through, and how long does the grant live? |
| HS-13 | A projection, read model, search index or cache is fed only by its consumer of events, is rebuildable, uses versioned upserts, is invalidated by event and version (never correct by TTL), is reconciled, and never becomes business truth. | Convention: rebuildable event-fed projection | Who writes each projection, and what makes it current? |
| HS-14 | Configuration and policy propagate by pull of a signed revision and a declarative, idempotent apply; the revision digest is the idempotency key and readiness is read from native status. No imperative script, no mutable runtime-global configuration. | OpenGitOps v1.0.0 3 | How does each configuration change reach its target? |
| HS-15 | A push to the browser comes from a projection fed by the durable channel, with resume from the last event id and a fallback to a synchronous read. The projection is never authority; nothing pushes from inside an owner transaction. | Convention: browser push from a projection | What feeds the browser push, and what is the fallback when the channel drops? |
| HS-16 | Across cells, sites or environments, data moves by the broker's store-and-forward replication: separate accounts per cell, globally unique ids, idempotent consumers on both sides, a bounded backlog with alerts. No direct cross-cell database access and no synchronous dependence on the other cell. | Enterprise Integration Patterns: Messaging Bridge | Does one environment's function depend on another being reachable? |
| HS-17 | Asynchronous work carries the decision id and correlation in the envelope, and the consumer acts as its own workload identity (token exchange for one audience where a user context is needed). User tokens are never forwarded in events. | RFC 8693 (OAuth 2.0 Token Exchange) | Whose identity performs each asynchronous effect? |
| HS-18 | Coordination (singleton consumer, migration, leader) uses native mechanisms only: the broker's single consumer, the orchestrator's lease, a database advisory lock, with lease expiry and fencing by revision. No home-grown lock. | Convention: native coordination primitives only | What serializes each singleton, and what happens when its holder dies? |
| HS-19 | Manual repair (quarantine release, re-drive, compensation) is an approved, audited flow that republishes the original reference with the same id, or runs the compensation, with actor and reason recorded, under current authorization. Never editing target data by hand, never a new id for an old event. | Convention: audited manual repair, same id | How does an operator re-drive or repair, and where is that recorded? |
| HS-20 | Replay, backfill and rebuild run from the channel's retention or an owner snapshot through the same consumers, rate-limited, marked as replay in the envelope; consumers are unchanged for it. No bespoke script writes to targets directly. | Convention: replay through normal consumers | By which path is lost or new downstream state rebuilt, and does any consumer special-case replay? |
| HS-21 | Deletion and erasure is a command to an orchestrated flow that fans out to each owner's native delete, each with a deadline and confirmed by an event, evidence retained, reconciliation proving zero rows. Assuming downstream copies expire on their own is prohibited. | Convention: erasure fan-out with proof | How is each downstream copy removed and proved gone? |
| HS-22 | Deployment and control-plane work is declarative, idempotent apply under the tool's native locking, results recorded as evidence. No concurrent probe during a converge, no imperative patching of instances. | Convention: locked declarative apply | What locks each apply, and can a probe or second run overlap it? |
| HS-23 | A converge-time bootstrap call (creating a user, a project, an identity-provider import, a store init) is a declarative state that is create-if-missing on a natural key (a guard read or a native declarative import), with an explicit timeout on the call and on the unit that runs it; the converge is the only retry owner. No append-style mutation, no unguarded POST, no retry or loop inside the script. | Convention: guarded create-if-missing bootstrap | What guards each bootstrap call against a second run, and what bounds it? |
| HS-24 | A shared control-plane record (host assignment, inventory, tenant record, DNS) has one writer; readers reread on their own converge; a change that needs action is published as an event; record is reconciled against effect. Never two writers, never a reader acting on a stale copy without a version check. | Convention: one writer per shared record | Who is the one writer of each shared record, and how do readers know it is current? |
