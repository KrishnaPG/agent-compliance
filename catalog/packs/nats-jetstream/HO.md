# NATS JetStream pack, HO rules

Pack `nats-jetstream` for base catalog 1.1.0. Scope: streams, consumers, message ids, users and accounts, dead letters. Loaded only when the project overlay names this pack. Each row is the whole rule.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| NJ-01 | A hand-off stream uses file storage, a replica count per environment class and a declared retention; a stream holding obligations sets `DenyDelete` and `DenyPurge` (which protect its messages), and no application user is permitted to call the stream delete or purge API. | NATS documentation: JetStream streams | What storage, replicas and retention does each stream declare? |
| NJ-02 | The `Nats-Msg-Id` header equals the event id. An answer to a command adds the command's stream sequence to the header, so a later re-execution's answer is not dropped as a duplicate. | NATS documentation: JetStream publishing (avoiding duplicate writes) | What is each publish's `Nats-Msg-Id`, and can a legitimate later message be dropped as a duplicate? |
| NJ-03 | Each producer and consumer has its own NATS user with publish and subscribe permissions limited to its subjects; accounts separate cells and scopes; all links use TLS. | NATS documentation: authorization, accounts | Which subjects may each user publish and subscribe? |
| NJ-04 | A hand-off consumer is durable with explicit acknowledgement, an `ackWait`, a bounded `maxDeliver` and a `BackOff` list no longer than `maxDeliver` with no jitter; redelivery is the one retry owner, and the only negative-acknowledgement delay is a provider's stated retry delay. | NATS documentation: JetStream consumers | What are each consumer's ack policy, `maxDeliver` and `BackOff`, and does anything else retry? |
| NJ-05 | The stream's duplicate window is a delivery optimisation, never the idempotency mechanism; every effect is idempotent by its own key. | NATS documentation: JetStream publishing (avoiding duplicate writes) | Does any effect stay single only because of the duplicate window? |
| NJ-06 | Where order matters, the consumer uses `maxAckPending: 1` per subject partition; a partition token comes only from the account's subject mapping, never from the publisher; a replay runs per partition while that partition's live consumer is paused. | NATS documentation: subject mapping and partitioning; consumers | What scopes each ordered consumer, and who chooses the partition? |
| NJ-07 | Users, accounts and subject mappings are declared in version control and reconciled against the declared list on every run; removing a user is a revocation first, then a deletion. | NATS documentation: decentralized authentication, revocation | How is a user or mapping added and removed, and what revokes a removed one? |
| NJ-08 | After `maxDeliver`, or on a non-retryable failure, a reference carrying stream, consumer, sequence, reason and correlation id is published to a dead-letter stream, and the original is acknowledged only after that publish has its PubAck. | NATS documentation: JetStream advisories; consumers | What is published where when a message is given up, and when is the original acknowledged? |
