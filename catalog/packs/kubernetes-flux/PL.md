# Kubernetes with Flux pack, PL rules

Pack `kubernetes-flux` for base catalog 1.0.0. Scope: one applier, dependency edges, health, intervals, Jobs, Helm, prune, secrets by External Secrets Operator, admission webhook. Loaded only when the project overlay names this pack. Each row is the whole rule.

| ID | Rule | Provenance | Test question |
|---|---|---|---|
| KF-01 | Flux is the only applier of in-cluster objects: every object is in the signed artifact Flux pulls, and nothing else applies, patches, scales, restarts or labels one (no out-of-band `kubectl`), except the minimal set that bootstraps Flux itself. | Flux documentation; OpenGitOps v1.0.0 | By what is each in-cluster object applied? |
| KF-02 | A Kustomization's `dependsOn` lists exactly its hard parents; an operator's Kustomization is a hard parent of every custom resource of its kinds; a dependent applies only against parents Ready at the same source revision. | Flux documentation: Kustomization `dependsOn`; kustomize-controller source (a dependency must have applied the current revision) | Is each dependency edge a real hard parent, and can a resource apply before its operator? |
| KF-03 | Every `dependsOn` points to the producer of the key or object actually read and stays current when that producer moves; a parent can never report Ready at an old revision to its child. | Flux documentation: Kustomization `dependsOn` | Who produces what each package reads, and is that the edge? |
| KF-04 | Health is the native status: a Kustomization lists health checks for its readiness objects; a custom resource is checked by a `healthCheckExprs` expression on its operator's own Ready condition (a custom resource without one is not waited on); a chart is checked as a HelmRelease; a PersistentVolumeClaim whose storage class binds on first consumer is not health-checked, because it stays Pending until a workload uses it. | Flux documentation: Kustomization health checks, `healthCheckExprs`; Kubernetes documentation: StorageClass volume binding mode | What reads each object as healthy, and is any custom resource unchecked? |
| KF-05 | `spec.interval` is Flux's required field and never a repair or drift path of ours; no Kustomization or HelmRelease sets `retryInterval` to get past an ordering gap; every Kustomization carries a timeout. | Flux documentation: Kustomization, HelmRelease | Does the design add or rely on an interval or retry override? |
| KF-07 | Converged means every Kustomization is Ready at its own pinned revision of the pushed artifact, read by an event-driven watch that fails fast on a terminal failure; Ready from a previous revision is a false pass. | Flux documentation: Kustomization status | Against which revision is Ready judged? |
| KF-08 | A reconciliation is woken by a Receiver call from the producer, by Flux's watches, and by the controller's own dependency requeue (its `--requeue-dependency` flag, default 30 s, the controller's setting, never shortened by us). Nobody annotates an object by hand to nudge it, and no source is polled at a short interval. | Flux documentation: Receiver (notification-controller); kustomize-controller options (`--requeue-dependency`) | What wakes each Kustomization after a push? |
| KF-09 | Every chart is a Flux HelmRelease: install uses `strategy.name: RetryOnFailure` (never install remediation, which uninstalls); upgrade remediates by `rollback` with `remediation.retries` set, never `uninstall`; the CRD policy (`install.crds`, `upgrade.crds`: Skip, Create or CreateReplace) is stated. | Flux documentation: HelmRelease remediation, CRD policy | Can a failed upgrade uninstall a chart, and how are its CRDs upgraded? |
| KF-11 | Flux owns its declared fields by server-side apply; a foreign field manager is removed only through the controller's override list, never by hand. | Kubernetes documentation: Server-Side Apply; Flux kustomize-controller | Who else writes fields of each object? |
| KF-14 | Images are referenced by digest; a workload rolls by a digest change or a checksum annotation on its configuration, never by a restart, scale or patch step. | Kubernetes documentation: images; Helm chart practice (checksum annotations) | What makes a workload pick up new configuration or a new image? |
| KF-16 | A value known only on the host reaches a manifest by Flux post-build substitution from one constants object (`postBuild.substituteFrom`); any other `${` in rendered output is escaped as `$${`, so no unintended substitution reaches Flux. | Flux documentation: Kustomization post-build variable substitution | Does any manifest value come from the host, or any unescaped substitution reach Flux? |
